## Why an import-only change is insufficient

The toolkit reads UTF-8 text and calls `load(string)` in `src/audit.ts:62`. The [full entry](https://github.com/cheeriojs/cheerio/blob/v1.2.0/src/index.ts) exports the default [parse5 loader](https://github.com/cheeriojs/cheerio/blob/v1.2.0/src/load-parse.ts); the [slim entry](https://github.com/cheeriojs/cheerio/blob/v1.2.0/src/slim.ts) uses htmlparser2. The official [configuration guide](https://cheerio.js.org/docs/advanced/configuring-cheerio/) explains the different parser behavior. Slim can change the runtime module/bundle graph; it does not change the package's declared installation dependencies.

The recorded string observation imported both supported entries without editing source. Both decoded the supplied UTF-8 title, named entity, numeric references, and attribute correctly. Full created one body and one tbody; slim created neither, demonstrating a concrete parsing difference. After importing slim, `whatwg-encoding` remained installed, and the installed dependency tree was unchanged. See `full-and-slim-string-observation.json` and `post-probe-tree.json`. This is a narrow parser observation, not the required real audit CLI regression or a claim of general equivalence.

## Separate XML decoder integration

TICKET-006 pins the already installed MIT-licensed `@nodable/entities@3.1.0` as a direct dependency for XML numeric references. This does not change the Cheerio chain or resolve BL-001. The installed fast-xml-parser 5.11.2 source sets `numericAllowed` from the deprecated `htmlEntities` option; `processEntities: true` alone leaves numeric references literal. Its published `entityDecoder` interface accepts the supported decoder instance. The [official decoder documentation](https://github.com/nodable/val-parsers/blob/main/Entity/docs/EntityDecoder.md) describes numeric reference support; the [parser source](https://github.com/NaturalIntelligence/fast-xml-parser/blob/v5.11.2/src/xmlparser/OrderedObjParser.js) and published TypeScript declarations were inspected. The integration enables numeric references with XML named entities and retains the prior 100,000-character expansion limit. The CLI red/green receipts demonstrate named/decimal/hex equivalence and single-pass escaping. DTD/custom entities remain rejected before parsing.
